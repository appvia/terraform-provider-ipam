# Azure/IPAM prior-art assessment

**Source baseline:** Azure/ipam `main` at [`12e41f4b93a7e5f3c61a859428c32137440037b2`](https://github.com/Azure/ipam/commit/12e41f4b93a7e5f3c61a859428c32137440037b2), corresponding to release [v3.6.0](https://github.com/Azure/ipam/releases/tag/v3.6.0). ## 1. Data model

### Spaces and Blocks

Azure IPAM stores each Space as a Cosmos document with internal fields:

- `id`: UUID generated by the engine
- `type`: `"space"`
- `tenant_id`: tenant partition key
- `name`: string
- `desc`: string
- `blocks`: array

The public `Space` model exposes only `name: str`, `desc: str`, and `blocks: List[Block]`; the persistence-only fields are added during creation. A Space is therefore a named aggregate rather than an independently addressable object with a public immutable ID. [models.py:260-301](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L260-L301), [space.py:631-641](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L631-L641)

A Block is embedded in its Space and has:

- `name: str`
- `cidr: str` / validated `IPv4Network` on input
- `vnets: List[VNet]`
- `externals: List[ExtNet]`
- `resv: List[Reservation]`

It has no separate database ID. New blocks initialize all three child collections empty. Blocks in one Space may not overlap. [models.py:207-258](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L207-L258), [models.py:308-313](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L308-L313), [space.py:1073-1100](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L1073-L1100)

The documentation defines a Space as a logical collection of unique, possibly noncontiguous Blocks; overlap is prohibited within a Space. [docs/how-to/README.md:37-68](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/docs/how-to/README.md#L37-L68)

### Azure Virtual Network association

A Block does not contain copies of Azure VNets. It stores lightweight references:

```text
VNet {
  id: string              // Azure resource ID
  active?: boolean
}
```

Expanded reads discover the Azure object and expose `name`, `id`, `prefixes: List[str]`, `subnets`, `resource_group`, `subscription_id`, and `tenant_id`. The same Block network mechanism also handles virtual WAN hubs. [models.py:105-112](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L105-L112), [models.py:165-193](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L165-L193), [azure.py:503-542](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/azure.py#L503-L542)

Associating a network validates that:

1. The Azure resource ID exists.
2. At least one discovered prefix lies within the Block.
3. Its CIDR does not overlap an outstanding reservation, external network, or existing associated network.

The stored association is then `{id, active: true}`. [space.py:1496-1573](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L1496-L1573)

### External Networks, subnets, and endpoints

These model non-Azure address use:

```text
ExtNet {
  name: string
  desc: string
  cidr: IPv4Network
  subnets: ExtSubnet[]
}

ExtSubnet {
  name: string
  desc: string
  cidr: string
  endpoints: ExtEndpoint[]
}

ExtEndpoint {
  name: string
  desc: string
  ip: string
}
```

Expanded forms add parent identifiers (`space`, `block`, and for subnets `external`). [models.py:117-158](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L117-L158)

External Network and subnet create requests accept either `cidr` or `size`, but not both; the server allocates the first suitable CIDR when only `size` is provided. Endpoints accept an explicit IPv4 address or `null`, with `null` allocating the next host address. [models.py:346-388](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L346-L388), [space.py:1821-1873](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L1821-L1873), [space.py:2426-2468](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L2426-L2468)

### Reservations

A reservation has:

```text
Reservation {
  id: string
  cidr: string
  desc?: string | null
  createdOn: float
  createdBy: string
  settledOn?: float | null
  settledBy?: string | null
  status: string
}
```

Expanded responses add `space`, `block`, and a computed:

```json
{"tag": {"X-IPAM-RES-ID": "<reservation-id>"}}
```

[models.py:194-230](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L194-L230)

Block reservation input supports:

- `size?: int`
- `cidr?: IPv4Network`
- `desc?: str`
- `reverse_search?: bool = false`
- `smallest_cidr?: bool = false`

Exactly one of `size` and `cidr` must be supplied. Multi-Block reservations instead require `blocks: list` and `size: int`; Blocks are considered in caller-specified order. [models.py:314-345](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L314-L345)

Observed status values include `wait`, `fulfilled`, `warnCIDRMismatch`, `errCIDRExists`, and `cancelledByUser`. Reservations are “deleted” by settling them with a cancellation status rather than physically removing them. [azure.py:860-942](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/azure.py#L860-L942), [space.py:3078-3090](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L3078-L3090)

### Exclusions

Exclusions are not CIDR exclusions. They are Azure **subscription IDs** excluded from Resource Graph discovery:

```text
Exclusions = List[UUID]
```

They are stored in the tenant’s singleton admin document alongside `admins`, exposed through `/api/admin/exclusions`, and injected into Resource Graph queries as `subscriptionId !in~ (...)`. [models.py:484-486](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L484-L486), [admin.py:237-368](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/admin.py#L237-L368), [helper.py:278-309](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/common/helper.py#L278-L309)

## 2. REST API, authentication, allocation, and reconciliation

### API shape

FastAPI mounts public routers under `/api`; OpenAPI is at `/api/openapi.json` and Swagger at `/api/docs`. Azure discovery and internal routes also use `/api` but are omitted from the generated schema. [main.py:410-474](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/main.py#L410-L474)

### Authentication and authorization

Every router depends on `api_auth_checks`. Requests must carry an Entra v2 bearer token:

```text
Authorization: Bearer <JWT>
```

The engine fetches tenant JWKS, validates RS256 signature, audience against `ENGINE_APP_ID`, issuer against the configured tenant, and rejects v1 access tokens. Tenant ID comes from `tid`; administrator status is determined by matching token `oid` against the admin Cosmos document. If no admins are configured, all authenticated users are treated as administrators. [dependencies.py:156-281](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/dependencies.py#L156-L281), [docs/how-to/README.md:5-31](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/docs/how-to/README.md#L5-L31)

Admin discovery uses the engine service principal; non-admin discovery uses an on-behalf-of credential and therefore reflects the caller’s Azure RBAC visibility. [helper.py:278-309](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/common/helper.py#L278-L309), [docs/README.md:19-35](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/docs/README.md#L19-L35)

### Requesting the next available CIDR

Canonical stateful allocation:

```http
POST /api/spaces/{space}/blocks/{block}/reservations
Authorization: Bearer ...
Content-Type: application/json

{
  "size": 24,
  "desc": "optional",
  "reverse_search": false,
  "smallest_cidr": false
}
```

Alternatively, send `{"cidr":"10.0.100.0/24","desc":"..."}` for a specific range. The engine subtracts associated Azure-network prefixes, outstanding reservations, and External Network CIDRs from the Block, then allocates the first or last suitable subnet according to the flags. [space.py:2891-3032](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L2891-L3032)

For ordered fallback across Blocks:

```http
POST /api/spaces/{space}/reservations

{
  "blocks": ["preferred", "fallback"],
  "size": 24
}
```

### `X-IPAM-RES-ID` reconciliation

The reservation response synthesizes `tag.X-IPAM-RES-ID = reservation.id`. The intended workflow is:

1. Create the reservation.
2. Use its `cidr` as the VNet address space.
3. Tag the VNet with `X-IPAM-RES-ID=<id>`.
4. A scheduled reconciler discovers the tagged VNet through Resource Graph.
5. If reservation ID and CIDR match and there is no conflicting associated VNet, it adds `{id: <Azure resource ID>, active: true}` to the Block and marks the reservation `fulfilled`, with `settledBy = "AzureIPAM"`.

The reconciler runs every minute in both App Service and Function hosting modes. ## 5. Project status and AVNM IPAM

Azure/ipam is maintained, not abandoned:

- v3.6.0 shipped September 11, 2025. [release](https://github.com/Azure/ipam/releases/tag/v3.6.0)
- The repository is not archived and remains open for issues and pull requests. [repository metadata](https://api.github.com/repos/Azure/ipam)
- A maintainer-authored v4.0.0 PR opened March 2026 remained active in October 2026, with 295 commits and a substantial framework/authentication/documentation overhaul. [PR #377](https://github.com/Azure/ipam/pull/377)
- A separate `ipam-3.7.0` branch and active 2026 pull requests also exist. [branches](https://api.github.com/repos/Azure/ipam/branches?per_page=100), [open pull requests](https://api.github.com/repos/Azure/ipam/pulls?state=open&per_page=20)

Azure Virtual Network Manager IPAM is a distinct **first-party Azure service**. It provides hierarchical root/child pools, up to seven pool levels, IPv4 and IPv6, automatic nonoverlapping allocation, static allocations, delegated pool permissions, and pool association with VNets. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/virtual-network-manager/concept-ip-address-management)

**Microsoft does not currently position AVNM IPAM as the formal successor or migration target for the open-source Azure/ipam project in the sources reviewed.** The clearest maintainer statement explicitly contrasts them: Azure/ipam is open source, while AVNM IPAM is a first-party Azure offering. It does not announce deprecation, replacement, or a migration path. [maintainer comment](https://github.com/Azure/ipam/issues/85#issuecomment-5283929165)

Architecturally, AVNM is nevertheless the strategic managed-service alternative: it is native ARM state with hierarchical pools and first-party allocation, whereas Azure/ipam is a customer-hosted FastAPI/Cosmos/Resource Graph application with Spaces, embedded Blocks, reservations, and tag-based eventual reconciliation. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/virtual-network-manager/concept-ip-address-management), [Azure/ipam architecture](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/docs/README.md#L12-L70)

## 6. Terraform-provider design implications

### Recommended resources

1. **`ipam_space`**
   - CRUD through `/api/spaces`.
   - Terraform ID should be the canonical Space name because the API does not expose the Cosmos UUID.
   - Name changes require state-ID replacement after PATCH.  
   Evidence: [Space model and CRUD](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L540-L738)

2. **`ipam_block`**
   - Parent-qualified ID such as `space/name`.
   - Resource fields: `space`, `name`, `cidr`.
   - Child arrays must remain computed and must not be sent during normal updates.
   - Deletion should surface the API’s nonempty-Block protection rather than silently force-delete.  
   Evidence: [Block CRUD](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L984-L1350)

3. **`ipam_external_network`**, **`ipam_external_subnet`**, **`ipam_external_endpoint`**
   - Natural parent-qualified IDs.
   - Support either explicit address or size-based allocation.
   - Allocated address/IP must be computed and persisted in state after create.
   - Changing allocation inputs should generally force replacement; otherwise Terraform may request a new allocation during update.  
   Evidence: [request models](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/models.py#L346-L388), [nested CRUD](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L1728-L2800)

4. **`ipam_block_network_association`**
   - Manage one VNet/vHub association per resource through POST and DELETE.
   - Avoid using PUT for an individual Terraform resource because PUT replaces the entire Block association list and would cause multiple resource instances to fight over ownership.
   - Import ID: `space/block/<azure-resource-id>` with escaping or a structured parser.  
   Evidence: [POST/PUT/DELETE semantics](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L1496-L1760)

5. **`ipam_reservation`**
   - This must be a resource, not merely a data source: POST performs the durable allocation.
   - Create at apply time, persist the returned reservation ID and CIDR, and read through `GET .../reservations/{id}`.
   - `size`, `cidr`, Block selection, `reverse_search`, and `smallest_cidr` should be replacement-only.
   - Export `vnet_tag = {"X-IPAM-RES-ID" = id}`.
   - Model `status`, `settled_on`, and `settled_by` as computed.
   - Do not treat transition from `wait` to `fulfilled` as drift; it is the expected reconciliation lifecycle.
   - Destroy can cancel an outstanding reservation, but a fulfilled reservation is historical and cannot reliably “release” the already-created VNet or remove its Block association. Document this explicitly.  
   Evidence: [reservation create/read/delete](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py#L2821-L3242), [reconciliation](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/azure.py#L860-L942)

6. **`ipam_subscription_exclusion`**
   - Prefer one logical set resource owning the exclusion list, or explicit merge-aware single-subscription resources.
   - A naive resource per UUID must avoid using PUT because PUT replaces the entire global list.
   - POST-add and DELETE-single are safer for independently managed instances.  
   Evidence: [exclusion API](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/admin.py#L237-L368)

### Recommended data sources

- `ipam_space`, `ipam_spaces`
- `ipam_block`, `ipam_blocks`
- `ipam_external_network`
- `ipam_reservation`
- `ipam_block_networks`
- `ipam_available_block_networks`
- `ipam_azure_networks` / `ipam_azure_vnets`

### Allocation and idempotency rules

- **Never allocate during plan or refresh.** Only resource Create should POST a reservation.
- **Store the server-generated ID immediately.** Retried Terraform creates must first reconcile any returned ID/state rather than blindly POST again.
- **Use reservation GET as the source of truth.** The CIDR is immutable provider state after creation.
- **Treat `404`/invalid-reservation responses as removal, but treat `fulfilled` as present.**
- **Use Cosmos concurrency behavior rather than client-side “next CIDR” calculation.** The API uses ETag `IfNotModified` replacement and retries access-condition failures up to five times, recomputing the operation; duplicating allocation client-side would weaken race safety. [helper.py:213-276](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/common/helper.py#L213-L276)
- **Canonicalize names case-insensitively for reads but preserve server casing in state.** API lookups generally compare `LOWER(name)` while some mutation paths use exact names internally. [space.py](https://github.com/Azure/ipam/blob/12e41f4b93a7e5f3c61a859428c32137440037b2/engine/app/routers/space.py)
- **Expect eventual consistency after VNet creation.** The provider should expose reservation state but should not poll with fixed sleeps; if a wait option is offered, poll boundedly for the exact `fulfilled`/error status transition.
- **Separate Azure resource lifecycle from IPAM lifecycle.** The IPAM provider should return the CIDR and reconciliation tag; `azurerm_virtual_network` remains responsible for the VNet.
