Cloud IPAM prior art, and what it means for a Terraform IPAM provider

ULW-research synthesis · as of 2026-10-28 · 8 research lanes + 1 skeptic · 397 URLs logged across 23 domains · primary sources pinned where possible

Answer. Three families of prior art exist. Azure/ipam is a self-hosted app (Space → Block → Reservation) that hands out CIDRs and reconciles them with a VNet tag [S1][S3]. AVNM IPAM is Azure's first-party, ARM-native pool hierarchy, where a VNet or subnet asks for a number of addresses and gets prefixes back [S9][S15]. AWS VPC IPAM is the most complete model: IPAM → scope → nested pools → provisioned CIDRs → allocations, plus discovery, Organizations, RAM sharing, and (since 2025) policies [S18][S22].

All of them push a provider toward the same shape:
  1. Allocation is a managed write at apply time that chooses and reserves in one step. It is never a data source and never a "next CIDR" preview.
  2. What you ask for is configuration and what you get is computed state. For example, prefix_length or an address count goes in, and cidr or allocated_prefixes comes out.
  3. Pool capacity, allocations, and consumer bindings are separate resources.
  4. Uniqueness is scoped to an explicit realm (scope, space, or VRF).
  5. Create must be idempotent, so retries can recover. This is the gap that bites the existing Azure/ipam provider [S7].
The skeptic argued, and I agree, that a backend-agnostic provider is a trap. The products disagree on request shape, result cardinality, identity, and release semantics, so portability belongs in modules over backend-specific resources.

2. Facts that matter most for schema design

Azure/ipam

  • Stateful allocation is POST /api/spaces/{space}/blocks/{block}/reservations, with exactly one of size or cidr. POST /api/tools/nextAvailableVNet only computes a CIDR and reserves nothing [S2].
  • The official Terraform example is unsafe. It uses an external data source that runs curl POST, so each refresh can create another reservation [S4][S47].
  • Reconciliation is asynchronous. You tag the VNet with X-IPAM-RES-ID. A job scheduled every minute (a schedule, not a latency guarantee) matches the VNet's CIDR, associates it, and marks the reservation fulfilled [S3].
  • An existing provider is already out there. XtratusCloud/azureipam v2.0.0 is built on the Plugin Framework and has 6 resources and 10 data sources [S6]. Its known problems:
    • It has a 10-second timeout and no idempotency key, and issue #16 reports a timeout even though the reservation was created [S7].
    • Reservation Update never calls the API.
    • Read returns an error on 404 instead of removing the resource from state.
    • It omits the Content-Type header, which v4 rejects [S8].
  • Azure/ipam v4 (PR #377) is still unreleased but in active development [S5]. It adds 4 routes and removes none, and makes reservation id nullable for rows redacted from non-admins. It returns 409 when a CIDR is unavailable and 503 in staging mode, and splits permissions between Admin and User. It stays IPv4-only.

AVNM IPAM

  • The pool request is a count of addresses as a decimal string (strings because IPv6 counts don't fit int64), and the result is a list of prefixes [S11][S15].
  • Native azurerm support arrived in four steps:
    • azurerm_network_manager_ipam_pool in 4.23.0
    • azurerm_virtual_network.ip_address_pool in 4.32.0
    • azurerm_subnet.ip_address_pool in 4.38.0
    • azurerm_network_manager_ipam_pool_static_cidr in 4.41.0
    AzureRM rejects decreases in the count on the client side, and suppresses the address_space diff only while the pool block is configured [S15][S16].
  • Regional GA was first verified on 2025-06-12 in the Microsoft Docs source history [S17]. Current docs show GA everywhere AVNM runs except six regions [S10]. Nothing we reviewed names AVNM as the formal successor to Azure/ipam. It is the first-party managed alternative.
  • unresolved Whether a count that isn't a power of two is really split into several prefixes (e.g. 80 → /26 + /28) is unproven. The only evidence is a REST spec example that contradicts itself: it requests 65536, echoes 800, and allocates a /22 [S14]. The list type is real, so model it as a list either way.

AWS VPC IPAM

  • AWS separates provisioning (adding a CIDR to a pool) from allocation (giving part of a pool to a child pool or resource). In Terraform these are aws_vpc_ipam_pool_cidr and aws_vpc_ipam_pool_cidr_allocation [S24][S25].
  • The non-overlap guarantee is narrow: AllocateIpamPoolCidr won't overlap another allocation in the same pool. Listing and release are eventually consistent [S19][S20]. The 32-minute delete timeout in the AWS provider belongs to pool-CIDR deprovisioning, which waits for VPC and subnet allocations to drain [S24].
  • aws_vpc_ipam_preview_next_cidr is the anti-pattern to avoid. It calls the API once at Create, Read just decodes state, and Delete does nothing. Parallel instances get the same CIDR [S26][S27].
  • The provider's ForceNew settings are right on pools (address_family, locale, source_ipam_pool_id, scope). [S23]
  • Recent additions keep stretching the model: IPAM policies, prefix-list resolvers, Infoblox as an external authority, allocation tags, and BGP/RPKI. See [S22]. In the research snapshot, the Terraform AWS provider had not yet added policy resources.

4. How this should shape your provider

Recommended resource and data source set

# realm / pool hierarchy        (AWS scope+pool, AVNM pool tree, Azure/ipam space+block)
resource "ipam_scope"       { name; description }                     # uniqueness realm
resource "ipam_pool"        { scope_id (RR); parent_pool_id (RR); address_family (RR)
                              allocation_rules { min/max/default_prefix_length; strategy } }
resource "ipam_pool_cidr"   { pool_id (RR); cidr XOR prefix_length (RR) → cidr (computed) }  # provisioned capacity

# allocation: the heart of it
resource "ipam_allocation" {
  pool_id        = ...        # RequiresReplace
  prefix_length  = 24         # XOR cidr; RequiresReplace (or RequiresReplaceIf grow-only)
  allocation_key = "app1-prod"# stable idempotency key, RequiresReplace
  description    = ...        # in-place
  # computed: id, cidr (UseStateForUnknown), status, consumers[], created_at
}
resource "ipam_external_reservation" { … }   # on-prem / non-integrated space (AVNM static CIDR, Azure/ipam externals, GCP EXTERNAL_TO_VPC)
resource "ipam_association"          { allocation_id; resource_id }   # explicit consumer binding, if the backend has it

data "ipam_pool" / "ipam_pools" / "ipam_pool_usage"   # usage split from the mutable pool (AVNM getPoolUsage pattern)
data "ipam_allocations"                                # filtered lookup for expressions
list "ipam_allocation"                                 # TF 1.14 terraform query → bulk import (optional; not in OpenTofu 1.13)
function "provider::ipam::cidr_contains" etc.          # pure math only, never "next available"

Schema rules drawn from the evidence

  1. Allocation happens only in Create. Never in Read, never in a data source, never in an action. Actions have no output you can reference and can't modify state [S45]. Provider functions must be pure [S46].
  2. Keep request and result in separate fields when they are different concepts, like a count versus a list of prefixes, or a length versus a CIDR. Optional+Computed on one field is fine when a single field can be either set explicitly or chosen by the server. AWS #45844 and #46795 were missing-Computed and update-branch bugs, not proof that the pattern is broken [S28].
  3. Server-chosen values are Computed with UseStateForUnknown, and allocation inputs are RequiresReplace [S42]. Use RequiresReplaceIf only where the backend really supports growing in place (AVNM count increases).
  4. Model results as lists where the backend can return several prefixes (AVNM). Use decimal strings or big integers for address counts.
  5. Use an immutable remote allocation ID as resource identity (TF 1.12+ identity plus a legacy import ID), never the CIDR alone [S43]. Prefer composite IDs like space/block/id over scanning every space.
  6. Recover ambiguous creates with a caller-supplied allocation_key stored on the server and searchable. If a create times out after it committed, look it up by key before trying again. A mutex in the provider protects only one process.
  7. Release is a state machine. Delete should wait until the allocation is gone, treat 404 as success, and document backend quirks: AWS release is eventually consistent, and Azure/ipam fulfilled-reservation deletes are no-ops.
  8. Scope uniqueness to a realm and give overlap its own explicit policy. NetBox VRFs allow duplicates unless you set enforce_unique, and GCP uses typed overlap exceptions. A realm ID alone doesn't define overlap behavior.
  9. Map error codes deliberately: 409 means exhausted or conflicting, so don't retry. 401/403 are auth failures. 429/503 get bounded backoff. Never replay a non-idempotent POST.
  10. The Terraform 1.14 extras stay optional. These are list resources and actions; OpenTofu 1.13 doesn't document either [S44][S48].

The strategic choice: which backend?

OptionAssessment
A. Backend-agnostic "cloud IPAM" provider (one ipam_allocation covering AWS, AVNM, Azure/ipam…)not recommended The backends disagree on request type (length, count, or CIDR), result cardinality, identity, ownership, release, and scope. A shared schema ends up either as a lowest common denominator or as a union of mutually exclusive fields, and switching backends always destroys and recreates. Put portability in a module that exposes allocated_prefixes, allocation_id, and scope over backend-specific resources.
B. Wrap AWS IPAM or AVNMredundant The aws and azurerm providers already cover both, with consumer-integrated allocation you can't reproduce from outside.
C. Provider for Azure/ipam (fork or contribute to Xtratus)clearest gap The current provider has idempotency, timeout, 404-handling, Content-Type, and import defects. v4 isn't released yet, so pin to its OpenAPI spec and push for a reservation idempotency key upstream.
D. Your own IPAM backend plus provideronly if you're building the service too If so, copy the AWS split (scope → pool → pool CIDR → allocation), GCP's strategies and exclusions, AVNM's usage and association reads, and AWS ClientToken-style idempotency from the start.

My recommendation is C if the goal is IPAM for Azure estates, or D if the goal is a multi-cloud address authority you control. In both cases, build the resource set and rules above around one backend's real contract instead of a lowest-common-denominator abstraction.

6. Gaps

  • No live AVNM test was run on multi-prefix decomposition, and Xtratus v2 wasn't tested against an Azure/ipam v4 container.
  • The ordering and concurrency guarantees of Alibaba's allocation API weren't checked.
  • The absence claims for IBM and DigitalOcean rest on one documentation set each.
  • Methodology limits: the attached browser was unavailable (BrowserSkill no-daemon), so lanes read primary docs and pinned source through direct fetches and shallow clones. Team mode was unavailable, so background task lanes were used instead. The fact-ledger and report-gate tooling wasn't run; sources are cited inline instead.
